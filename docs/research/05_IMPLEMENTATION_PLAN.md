# 三天研究原型计划

制定日期：2026-10-19。目标：在 10 月 21 日前形成可演示、可复现、足以支撑项目方案的原型。不是在三天内证明普适有效性。

## 交付标准

1. 保留 Desktop Buddy，独立研究控制台复用其真实传感器源码。
2. 能明确同意、开始/停止本地采集、保存标签、查看和删除记录。
3. A/B/C 在同一特征轨迹、同一候选事件上运行；输出可核对的逐事件原因与指标。
4. 真实试验与合成测试明确分开；未测到的结论保持空缺。
5. 一份英文项目方案能说明问题、已有工作、方法、初步观察、限制和下一步。

## 第一天：闭环与可运行性

已实现但仍需用户实机体验：
- `tools/research/ResearchConsole.swift`：原生 SwiftUI 控制台，默认不采集；每 2 秒轮询，JSONL 保存粗类别、空闲、几何全屏、短期切换和稳定时间。
- `tools/research/run.command`：直接编译主应用现有模型/协议/传感器，不复制代码，不改主应用工程文件。
- 支持 5/30/60/180 秒后记录固定内容的模拟候选；之后标注候选当时的活动、是否希望立即提醒、是否有用、容忍延迟。
- `evaluate.py`：纯本地 A/B/C 回放、理由、延迟、到期处理、未完成随访计数。
- 9 项边界测试通过；原项目 xcodebuild 测试通过（有一项需显式开启的 live adapter 测试跳过）。

仍未完成：控制台完整手动场景验证、真实性能对照、用户录制、语义活动识别。语义识别当前统一 unknown，不以应用名冒充真实活动。

## 第二天：小型真实试验与修订

由用户先录制 2–3 段，每段 3–5 分钟，检验字段和标注是否可用，再扩展至六类场景。每个候选后至少留出 120 秒轨迹以完成模拟送达观察；最后一个候选不要紧接着停止。场景和候选顺序预先确定，避免只在“好时机”点击候选。每段 1–2 个候选，普通与紧急都覆盖。

如果 5 秒切回窗口或段后回忆造成明显偏差，优先调整协议，不追求漂亮指标。调规则录制与评估录制分开。采集 CPU、内存、采样耗时；新控制台是独立进程，其总开销与主应用开销分别报告。必要时将主应用通知作为真实体验展示，但不能把影子模拟算作真实通知实验。

## 第三天：方案和演示

- 冻结政策版本及脚本，保留可复现运行命令。
- 根据实际报告填写 06_RESULTS.md，记录失败与未完成观测。
- 完成英文项目方案和 1 页 HiLab 研究摘要。
- 准备 2–3 分钟演示：宠物载体 → 控制台采集 → 一个有标签的候选 → 三政策不同建议 → 报告与限制。
- 研究定位：有限且本地的上下文能在什么条件下帮助判断交互时机？不预先断言时间历史必然更好。

## 重要限制

当前研究工具每 2 秒轮询，可能漏掉间隔内的快速切换；switchCount 是观测到的次数，不是完整系统事件计数。控制台前台时数据被标为 research_console，防止把标注操作当成任务活动。全屏 false 不能排除元数据不足。本地删除策略在下次启动采集时执行，应用不运行时不会自动删除。主应用原有采样依然独立运行，后续若集成需共享采样以降低重复开销。

第一版政策全部是设计假设，C 的 10/60 秒和 3 次切换阈值尚未校准。A 的静态政策为普通候选立即通知；第一版未加入固定冷却，候选由实验协议控制间隔。各政策均不使用用户标签决策，统一 120 秒上限、紧急立即处理。没有永久 suppress，因为本实验尚未定义可自动删除的通知类别。用户 suppress 标签仍参与一致性评价，暴露这一局限。

## 交付语言（用户已确认）

日常沟通用中文。最终给 UCLA HiLab 的 proposal、research summary、demo script 和结果展示使用英文。02 和 04 文档及 HTML 报告已采用英文；最终申请材料将在真实试验后补齐结果，不能把合成测试数字填入用户实验结果。
